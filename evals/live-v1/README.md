# 真实客户端评测 live-v1

这组评测启动项目的 NeoForge Minecraft 客户端，在新的集成服务器世界中生成同伴，将玩家目标送入真实 AgentLoop，使用指定 ProviderLibrary 配置调用模型，再由服务端读取实际世界状态判分。它补充 `bot-v1` 的分层测试；后者的脚本模型成绩不能代替这里的真实模型成绩。

**历史证据与当前代码：**本页归档运行来自 `f39ee4d9bfa0` 加当时工作区源码，包含用户已有改动；每次实际候选以归档的 `candidate`、`source_sha256` 和 `source-hashes.json` 为准，并非 `f39ee4d9bfa0` 的干净检出。本 PR 基于 `origin/main` 的 `2443a255` 移植评测，本页成绩及 `verification*.json`、`survival-verification.json` 中的历史检查不代表最终 PR 或最新主分支已重新运行。当前代码的构建／测试和新模型运行需单独记载；旧结果不改写成新版本成绩。

## 场景与评分

| 场景文件 | 玩家目标与成功标准 | 用途 |
| --- | --- | --- |
| `scenarios/craft-planks.json` | 初始背包仅有 2 个橡木原木，最终背包至少有 8 个橡木木板 | 最短完整链路冒烟测试 |
| `scenarios/initial-survival.json` | 普通世界空背包出发，持有石镐、熔炉、8 个火把、3 个熟牛肉，同时生命 ≥ 10、饱食 ≥ 12 | 初期生存与依赖安排的探索性长任务 |
| `scenarios/sustainable-survival.json` | 普通世界空背包出发，建立工具、工作站、小麦田、亲自收割与原地补种、食物储备和安全据点，同时维持生命与饱食 | `survival-v1`：干净环境正式试跑因时间预算耗尽结束，记录到 1/6 个里程碑，任务未完成 |
| `scenarios/defeat-dragon.json` | 普通世界空背包出发，由同伴击杀至少一只末影龙 | 长程目标脚手架；不代表当前工具已覆盖完整通关机制 |

成功条件由同伴的实际背包、生命、饱食、位置、击杀统计和场景指定的世界观察器检查，不能靠模型声称“完成”通过。多个条件必须同时满足，数量是“至少”；`items` 要求物品仍在同伴背包中，世界条件则按下面的观察协议检查。里程碑记录第一次达到条件的时间与快照，不要求按列表顺序完成，也不替代最终条件。只向模型发送 `prompt`，不把里程碑列表变成行动步骤；可持续生存场景的提示公开全部成功标准，由模型自行决定行动方案。

首次死亡即失败，不允许靠自动复活恢复成绩。达到显式预算上限记为 `budget_exhausted`。`success`、`failed`、`budget_exhausted` 是有效的任务结果；启动、配置和观察异常记为 `infra_error`，人工中断记为 `cancelled`，不当作能力零分混入成功率。启动器的非正常退出会使 `run.json` 记录基础设施异常，同时保留客户端已写出的结果和轨迹。

全部样例为开发者编写并已阅读的 **dev** 样例，固定种子，单次运行、无人工救场。当前没有独立测试集，没有经过多种子验证的总体成功率，也没有已验证的真实模型通关基线。若更改目标、世界、评分或预算，应作为新的可比较配置重新测量，不能与旧记录直接合并。

## 可持续生存场景 survival-v1

`live.sustainable-survival` 是第一组把**可再生食物循环**纳入世界判分的长程场景：不仅持有食物，还要留下能继续生长的农田，并有同伴亲自收割、在原处补种的证据。它使用种子 `73002` 的普通世界、空初始背包，不预置物资、建筑或农田。旧的 `initial-survival` 保留为背包物资探索案例；两个版本分别记录，旧成绩不能当作新的生存成绩。

最终需要同时满足生命 ≥ 10、饱食 ≥ 12，以及以下世界条件：

| 条件 | 服务端观察协议 |
| --- | --- |
| 可用工具 | 背包里有剩余耐久、能正确采集铁矿的镐，以及仍可用的锄头；金镐不计为合格镐 |
| 工作站 | 附近已放置至少 1 个工作台和 1 个原版熔炉，背包里的方块不算 |
| 生长中的农田 | 至少 8 株小麦，下方是当前湿润耕地；耕地水平 4 格内、耕地或作物高度存在水；作物位置原版当前光照值 ≥ 9 |
| 收割与补种 | 至少 3 个不同位置的成熟小麦由本同伴实际破坏，然后在同一维度、原坐标观察到其重新种下的未成熟小麦；仅找到现成农田不能满足这项条件 |
| 安全食物储备 | 背包可安全食用物品的饱食恢复值 × 数量合计 ≥ 20；有概率产生负面效果的食物和带负面效果的谜之炖菜不计入 |
| 庇护所 | 同伴身处有照明、无室内怪物或危险方块、可通过可手动开关的门出入的封闭据点，几何要求如下 |

工作站和小麦仅在同伴当前所在维度的**已加载区块**里统计：水平 X、Z 轴各不超过 24 格，竖向不超过 8 格，不为判分额外加载远方区块。收割证据由实际破坏成熟小麦的事件确认；补种还核对放置归属。产品会将建造成果归给主人，因此隔离场景允许同伴或其主人名下的放置记录，主人保持旁观者并不手动种植。最多保留 256 个历史收割位置，最终要求 3 个不同位置的有效补种记录。

庇护所观察器采用保守的形状标准：当前脚下高度平面、水平 X、Z 轴各 ±8 格内的单层简单矩形空间，连续可通行地面最多 64 格，至少含一片 2×2 的可站立空地；各可站立格有两格净空、实地板，屋顶距脚下高度为 2～5 格且连续完整，边界由实心墙或关闭的可手动开关的门围住。至少一扇门可手动打开，内侧连接室内可站立区域，门外可站立且通向露天；各可站立格的 **BLOCK 光照 > 0**，室内没有 MONSTER 类实体。室内和脚下地板排除所有液体及含水方块，以及火、灵魂火、岩浆块、仙人掌、甜浆果丛、凋零玫瑰、细雪、营火、灵魂营火、滴水石锥；熄灭营火也保守排除。工作台等占地物可以留在室内；高低地板、斜屋顶、露台入口等复杂建筑暂不认可，不能把这种形状限制解释为 Minecraft 中所有安全建筑的定义。

世界快照约每 200 毫秒采样一次，每次重读固定半径的已加载区域，不沿用上次位置的缓存。全部最终条件必须在这些连续观察中保持 **1200 个游戏 tick**，中途条件不满足就重新计时，不能依赖瞬时凑齐物资通过。正常 20 TPS 时约为 60 秒，卡顿时真实耗时更长；采样之间的短暂变化可能不被观察到；两次观察相隔超过 20 游戏 tick 时，持续计时也重置。工具、工作站、农田、补种、食物储备和安全据点各有里程碑，里程碑不要求按表格顺序完成。

本场景的首条真实模型试跑因下述环境污染中止，不计正式成绩；修复后已取得一条**干净环境下因时间预算耗尽而未完成任务的基线**，详细结果见下一节。场景旨在验证一次收割与补种后具备继续生长的条件，不证明无限期生存或多个完整农业周期。默认不要求熬过整夜，也不涉及末影龙。当前自动吃饭尚未实现，模型需要自行安排进食；若因此饱食降到门槛以下，评分会如实体现，不向评测专门注入自动补给策略。

原试跑以总计约 30 分钟、100 次请求尝试、300 万个已报告 token 为预算范围。扣除中止首段的已观察消耗后，先完成零付费本地脚本校准，再完成一次上限为 **80 次请求、1700 秒、260 万个已报告 token** 的正式重试。下面命令用于准备相同场景与预算，保留 `--prepare-only`，不会再次启动游戏或调用模型：

```powershell
python -B tools/run_live_eval.py --prepare-only `
  --providers build/evals/live-model/providers.json --provider-id eval-model `
  --scenario evals/live-v1/scenarios/sustainable-survival.json `
  --max-model-calls 80 --max-seconds 1700 --max-tokens 2600000
```

场景的 `evaluation_version` 为 `survival-v1`，`world_observer` 为 `sustainable-survival-v1`；运行记录应保留这两个标识和实际预算，与旧版木板基线分别解释。

## 环境污染与成绩边界

首条可持续生存试跑位于 `build/evals/live-v1/20261003T021202919920Z-7562409a`，任务观察时间不到 73 秒时中止。中止前观察到 **14 次请求尝试、13 份用量报告、324318 个已报告 token**。这些消耗计入本次整体预算，但这条运行不计正式能力成绩，不能当作模型生存失败或有效基线。

原因是 NeoForge 开发客户端在 `runClient` 时也发现并静态初始化 GameTest 类，将测试夹具注册进了真实模型可见的工具环境。模型调用了测试工具 `gt_linger`，它替换了正在执行的 `mine` 任务，污染了本应只包含产品工具的评测过程。

修复仅在指定 `numenLiveEval` 的客户端评测构建中排除 core 的整个 GameTest Java 包；移植到当前主分支后，还排除 pathing 的 gametest sourceSet 及其编译依赖。普通开发客户端与 `runGameTestServer` 仍保留完整测试。评测在首次模型调用前将实际 `registered_tools` 列表与 `registered_game_tests` 数量写入 `fixture` 事件；只要已注册 GameTest 数量不为 0，就立即以 `infra_error` 结束，不调用模型。后续成绩必须带有这份环境证据，不能与受污染环境的记录直接比较。

修复后的本地脚本校准已成功：**401.9933 ms、0 个 GameTest、42 个工具且无 `gt_` 工具**，记录在 `baselines/survival-clean-calibration/`。它使用固定 localhost 回复与合成用量，仅证明干净环境下运行器能够驱动真实合成，`real_model=false`、`capability_baseline=false`。污染首段则保存在 `baselines/survival-interrupted-fixtures/`，明确标注外部中止；其中原始进度仍为 `running`，没有补写或伪造 `result.json`。

正式重试实际已报告 2481209 token，两段真实生存运行的已报告合计为 2805527，处于约 300 万的原预算范围内。被取消或失败的请求缺少用量，最后一次调用也可能越过阈值，因此这个合计不能保证完整 token 消耗或支持费用报价。能力成绩只采用干净环境正式运行；污染首段的消耗仍计入实验预算。

## 已记录的真实模型冒烟证据

下面的木板合成记录保留真实物理成功证据，但来自同类 NeoForge 开发环境，**当时也可能包含测试工具**。它不是修复后已核验工具表的正式可比基线；后续干净环境的结果应单独记录，原始归档不改写。

2026-10-03（Asia/Shanghai），通过 B.AI 接口、已配置代理运行 `deepseek-v4.1-flash`，完成一次 `live.craft-planks` 开发样例。服务端独立观察确认同伴背包由 **2 个橡木原木变为 8 个橡木木板**，任务耗时 **5081.8688 ms**，因此物理任务判定成功。原始结果保存在 [baselines/deepseek-v4.1-flash-smoke/results/result.json](baselines/deepseek-v4.1-flash-smoke/results/result.json)，完整验证汇总见 [verification.json](verification.json)。

这次预算为最多 10 次请求、300 秒、300000 个已报告 token，实际发起 **2 次 API 请求尝试**，其中 **1 次返回用量：输入 18479、输出 268，合计 18747 token**。合成完成后已经开始的后续请求，在世界成功条件被观察到时取消，未取得完整用量，因此 `usage_complete=false`，总费用仍为 `null`；18747 只是已观察到的用量，不能当作本次完整消耗。

首个模型回复耗时 4863.3977 ms，内容是合成工具调用。评测没有验证自然语言“完成”回复是否正确，也没有把这个时间称为“正确回答时延”。启动前只读 `GET /models` 预检返回 HTTP 200，确认接口列出选定模型，预检本身没有推理请求，记录见 [verification/model-preflight.json](verification/model-preflight.json)。

该结果仅证明**单个固定种子的合成样例**发生过真实模型驱动的物理成功，不证明其开发环境工具表已经排除测试夹具。空闲跟随、推理中改口、后台任务中返回、按钮／自然语言停止、遇袭自保的专门真实模型响应评测，以及旧版背包物资生存、击杀末影龙长任务，均仍为 **未运行**。可持续生存已按前述污染中止、干净环境校准和正式未完成结果分别记录。本地脚本响应的早期校准保存在 `baselines/harness-calibration/`，明确使用合成 token 用量，不混作真实模型能力成绩。

## 凭据与准备

沿用游戏里的 `config/numen/providers.json`，文件结构是 `{"entries":[...]}`。通过 `--provider-id` 选择条目的 `id`，不是界面显示名或提供商类型。API Key 留在本地文件，不放进命令行或聊天。仓库中的私有模板位置可使用 `build/evals/live-model/providers.json`；此目录被 Git 忽略。

先做无模型调用的准备检查：

```powershell
python -B tools/run_live_eval.py --prepare-only
```

也可以检查选定配置、场景和预算，但仍不启动游戏：

```powershell
python -B tools/run_live_eval.py --prepare-only `
  --providers build/evals/live-model/providers.json --provider-id eval-model `
  --scenario evals/live-v1/scenarios/craft-planks.json `
  --max-model-calls 10 --max-seconds 300 --max-tokens 300000
```

未提供配置或预算时，准备记录列出 `blockers`，状态为 `prepared`，不生成能力得分。执行前必须补齐三个预算参数以及非空的 provider、model、api_key；未补齐时启动器拒绝运行。提供商别名与协议由项目自身的 ProviderRegistry 解析，模型名称允许项目支持的自定义值。网络和鉴权是否可用只能在真实调用时验证。

启动器仅复制选中的一个条目到本次新建的 `game/config/numen/providers.json`；不复制原配置库里的其他条目、聊天、存档或记忆。每次运行使用独立的新目录和新世界。输出只能位于仓库 `build/evals/live-v1/` 下，拒绝复用已有目录。

## 运行

下面是一次冒烟运行的具体预算示例；只有在选定模型和预算后才执行。删除 `--prepare-only` 才会启动真实客户端并产生模型请求：

```powershell
python -B tools/run_live_eval.py `
  --providers build/evals/live-model/providers.json --provider-id eval-model `
  --scenario evals/live-v1/scenarios/craft-planks.json `
  --max-model-calls 10 --max-seconds 300 --max-tokens 300000
```

底层入口是 `:core:neoforge:runClient --no-daemon`。如果默认 NeoForge 依赖不可下载，而本机已有 `21.1.233` 缓存，可以显式添加 `--offline --neoforge-version 21.1.233`。该选项不修改 `gradle.properties`，但必须作为不同运行环境记录。**`--offline` 仅限制 Gradle 下载；真实模型仍会联网。** 客户端需要可用的 Java、图形环境和已满足的 Gradle 依赖。

`--max-model-calls` 限制真实 HTTP 请求尝试次数，包含自动重试。`--max-seconds` 限制世界准备完成后任务的真实时间，游戏不会像 GameTest 一样加速；启动器另给默认 600 秒启动时间，可用 `--startup-seconds` 显式调整。外层超时或 Ctrl+C 只结束启动器拥有的进程树并保留产物。

`--max-tokens` 是已报告的输入加输出 token 阈值。完成一次模型调用后才能获知其实际用量，因此最后一次回复可能超过阈值，这不是严格费用上限。若服务未返回用量，标记 `usage_complete=false`，停止发起下一次请求或执行下一项模型工具，并记为基础设施异常；已被独立世界观察确认的成功仍可保留。未知费用保持 `null`，不当作 0。所有预算来自 CLI，场景文件不能自行授权模型消耗。

## 记录与复核

每次运行目录包含：

- `request.json`：确切场景、预算、选中条目 ID、新世界名和输出位置，不含密钥。
- `run.json`、`source-hashes.json`：启动状态、候选源码哈希、环境覆盖、命令和退出信息。
- `launcher.log`：Gradle 与客户端标准输出；选中 API Key 在写入此日志前脱敏。
- `results/result.json`：客户端结果状态、原因、初末世界快照、里程碑、调用数和 token 用量。
- `results/trace.json`：按任务开始后毫秒计时的观察与事件轨迹。
- `results/trace.jsonl`、`results/progress.json`：每秒刷新的部分证据，异常退出时也可复核。
- `game/`：本次世界和本地配置，**包括私有凭据**。分享结果时不要打包整个运行目录。

`first_reply_ms` 只是第一条模型回复的时延，不证明回复正确；`correct_response_ms` 保持未测。完整的停止、插话和遇袭响应 benchmark 仍需带事件注入与专门判分的场景，不能从合成木板的运行中推断。

启动器检查结果属于本次场景与预算，并拒绝将缺失结果、旧结果、未结束状态或缺少轨迹的运行当作已完成。`prepared` 只证明离线输入准备成功，不能称为真实模型基线。

## 当前边界

这是复用产品真实链路的实验运行入口，不为评测添加游戏策略。旧版初期生存场景固定了牛肉这一种食物，不能代表所有地形和食物来源；它测“达到明确物资状态”，没有证明长期可持续生存。主人在评测中以旁观者停在初始位置，但工具在服务端按同伴 UUID 定位执行，不能把客户端远距离看不到实体直接当作工具无法继续执行的依据。世界判分仍只读取已加载区块，跨区探索是否持续推进需要真实运行证据。完整末影龙路线涉及跨维度、传送门、结构定位和战斗机制，场景定义不等于这些能力都已实现或可用。

目标通过产品现有的 `/goal` 入口运行，沿用最多 30 轮目标推进、连续 2 次停滞后收工的规则；运行器不会自动重开目标绕过这些限制。当前主分支在产品目标判定包含可机检宣称时，还会调用 `verify` 工具核对，核对未通过则继续推进；没有可机检宣称的判定不会走这一步。产品目标判定与核对影响续跑或收工，不能替代评测的独立世界判分。若大脑提前收工但场景条件未满足，本版继续观察到预算截止。

当前工具接口已按命令组组织，例如合成通过 `command` 调用 `inv craft`，并包含 `verify`、`routine` 等归档之后的产品行为。工具定义或目标判断改变都可能影响模型选择和用量，因此新运行应保存实际 `registered_tools` 并重新取得结果，不能沿用旧候选的 42 工具清单或把其未完成原因直接视为最新主分支的问题。

木板案例已保留一次真实模型驱动物理成功的证据；可持续生存已完成排除测试夹具后的校准与正式有限重试，得到可复核的未完成基线。整夜生存、多个完整农业循环和末影龙进度仍未验证。末影龙场景只供显式选择并配足预算的长跑，不会作为默认冒烟任务自动启动。

启动器离线验证命令（不调用模型）：

```powershell
python -B tools/test_run_live_eval.py
```

运行器本身可用本机固定 SSE 回复校验，仍会实际启动 Minecraft 并执行合成：

```powershell
python -B tools/calibrate_live_eval.py --offline --neoforge-version 21.1.233
```

该脚本只向 `127.0.0.1` 发送模型协议请求，按当前接口返回预定的 `command`（`inv craft minecraft:oak_planks --count 8`）调用及合成用量数据，不需要付费模型配置。结果本体标注 `calibration_only=true`、`real_model=false`、`usage_is_synthetic=true` 和 `capability_baseline=false`；它验证运行器接线，不测模型能力。历史校验已观察到库存由 2 个原木变为 8 个木板并自动保存退出，但使用的是当时的 `craft` 工具接口；归档结果与测试记录见 `verification.json`，不能据此声称当前接口适配已完成重跑验证。
