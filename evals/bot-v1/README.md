# Bot 最小评测 v1.2

固定样例和评分见 [cases.json](cases.json)。18 个可执行样例分为三个层次；另外 10 个完整玩家场景明确登记为未运行，不把它们从覆盖清单里删掉。

## 当前入口与历史边界

规划层运行真实 `ScriptEngine.IN_USE` 和当前产品发布的 `core/common/src/main/resources/modules/inv.lua`，直接调用 `numen.inv.make(item, count)`；所需移动辅助模块同样读取实际 `move.lua`。配方、原子库存变更与工作站来自有限夹具，夹具不递归展开配方，不代写行动方案，也不替模块采集。模块源码 SHA256、实际 API 轨迹、错误值及最终库存随逐例结果保存。

六个原目标、起始库存、可采资源和成功条件全部保留。当前 `numen.inv.make` 从已有材料中选择可做的配方并处理工作台；它不提供旧规划器的递归采集、兄弟依赖分配或批量余料规划，也不承诺在多配方时返回歧义。缺少这些能力时照实记录 `success=false`，不能用预写的计划或恢复未接入产品的旧 Java 规划器制造通过。缺工作台时明确失败且保留材料，仍按原“诚实失败”判据评分。

响应层继续使用当前真实 `AgentLoop` 与上游 `LoopHarness`，脚本模型的工具调用改为当前 `lua` 工具及 `numen.move.follow`、`numen.work.dig`、`numen.use.block`、`numen.task.stop` API。六项循环行为期待不变；模型与身体仍是夹具，不因调用写成 Lua 就计作现场语义理解或身体成绩。

下面的分数、依赖阻塞及 [verification.json](verification.json) 均为历史验证，不能当作当前源码的验证。新入口应由本次运行产生新的记录；即使样例版本仍为 `bot-v1.2`，评价器摘要已变化，不与旧分数直接合并或作等价模块比较。

## 运行

在仓库根目录运行，Python 只用标准库，Gradle 使用项目已有 Java/JUnit/Minecraft 依赖：

```powershell
# 默认最小路径：实际发布的 Lua 合成模块 + AgentLoop，世界/模型/工具为明确标记的夹具。
python -B tools/run_bot_eval.py --layer jvm --offline

# 加入真实 Minecraft 身体。首次准备依赖时去掉 --offline。
# 新检出须先生成数据资源；不能靠主工作区的被忽略文件。
.\gradlew.bat :core:neoforge:runData --no-daemon --offline
python -B tools/run_bot_eval.py --layer all --offline

# 本机已缓存并用于本次身体基线的显式替代环境。
python -B tools/run_bot_eval.py --layer all --offline --neoforge-version 21.1.233

# 评分记录校验器自身的测试。
python -B tools/test_run_bot_eval.py -v
```

默认输出 `build/evals/bot-v1/<UTC时间>/`，也可用 `--output <新目录>`。拒绝覆盖已有目录。两个 Gradle 命令顺序运行，均使用 `--no-daemon`。JVM 上限 10 分钟，完整 GameTest 上限 30 分钟；超时停止本次进程树并保留记录。`--neoforge-version` 只作用于该次命令，**不会修改 gradle.properties**。

退出码 0 表示评测执行和记录完整，**不表示所有业务样例通过**；业务失败读取 `success=false`。退出码 2 表示运行、记录或回归检查存在异常。身体层复用完整 GameTestServer，因此原有 GameTest 失败也会让整轮 `valid_run=false`，不能将仅六个新样例通过描述为全套回归通过。

## 目前到底能测什么

| 层次 | 实际入口 | 能说明什么 | 不能说明什么 |
|---|---|---|---|
| planning，6例 | 真实 `ScriptEngine.IN_USE` → 产品实际 `numen.inv.make` 模块 → 有限原子 API 夹具 | 同样六个目标上的实际模块行为、库存扣减与无法完成时的错误；递归依赖能力缺口照实低分 | 不提供测试内置规划器；手写配方子集不是 Minecraft 配方管理器，不能当作游戏内 LLM 规划得分；历史旧 Java 规划器分数不可替代当前分数 |
| response，6例 | 真实 `AgentLoop.push/halt`，复用 `LoopHarness` | 输入何时送模型、旧工具是否仍派发、取消和迟到回调处理 | 脚本模型不测语义理解；虚拟等待不是真实模型、客户端 UI、网络或身体延迟 |
| body，6例 | GameTest 内真实已注册工具和 `CompanionTickDispatcher` | 实际移动、停稳、替换返回、独立定时器、自卫抢占及任务不复活 | 没有真实模型或玩家 UI；当前停止/返回用例在走路中，尚不是采矿整链；战斗用例为持剑反击，尚未覆盖低血量逃跑 |
| live，10例 | 当前产品真实入口为客户端 `EntityAgentLoop` | 场景与预期已固定，待接入客户端+模型+可重置世界 | 目前全为 `not_run`，不产生质量或延迟成绩 |

代码审计与实际运行需要区分：

- 游戏中已有 `numen.inv.recipes/craft`、容器 API、`numen.work`/`numen.move` 模块、任务替换和自卫本能。可以组合出用户的场景，但原语存在不证明模型能正确组合。
- 当前组合逻辑属于实际发布的 Lua 模块或模型写出的程序；高层模型是否改变采集方案尚未测量。
- 上游已删除未接入产品的 `agent.plan`、行为树及旧验收孤岛。评测不恢复这些生产类；规划层改从当前真实模块观察相同业务目标。
- 通用 `LiveEvalRun` 场景判分与当前程序结构化回执仍各按自己的入口使用；最小路径利用 JUnit 和 GameTest 的直接世界断言，不借模块或模型自称成功判分。
- 心智模型文档描述的“旧模型回复→工具批完成→新输入注入”仍与当前循环一致，但与本次用户确认的“改口后不得执行过时指令”要求不同。本轮保留这个失败证据，没有改文档或产品行为。

## 样例与评分

全部是根据用户举例、原版配方和既有 GameTest 手工构造的 **dev** 样例。配方数量已与本地官方 Minecraft 1.21.1 JAR 中的数据核对。作者看过题目及答案，没有独立验证集或测试集，也没有泛化能力统计结论。每例一次，不通过重复确定性夹具制造样本量；游戏身体数据仍有寻路线程/调度波动，只能视为一次基线观察。

- 主指标：每层的场景判据符合率，每例等权。不同层不合并成“总智能分”。规划的工作站缺失、配方歧义两例把正确报告无法完成视为符合判据，不能称为物品制造成功。
- 规划评分：独立检查最终库存和有限采集额度，原子合成严格扣料，不能凭脚本跑完或“完成了”的自述判分。可采资源不自动进入库存；当前模块不采集时该差额仍不满足原判据。共享资源例测单目标的兄弟依赖；完整多目标仍列在 `live.shared_resources`。
- 响应评分：依据实际事件和端口调用。用户确认的要求是停止旧任务后保留自保、脱险不续做；模型推理中改口后不能派发过时指令。自然语言停止例测循环入口是否有即时取消；不把脚本返回 `task_stop` 算作模型理解成功。
- 身体评分：独立读实际位置、生命值、任务状态、伤害归因和事件。停止须连续三刻每刻移动小于 0.01 格，再在 40 刻观察窗内不离锚点 0.15 格且旧任务不复活。战斗敌人关闭随机 AI，但伤害、自卫寻路和攻击都走真实游戏入口。
- 延迟：`fixture_*` 是注入的虚拟时间；`component_micros`/`local_execution_ms` 只含本地组件和夹具；`body_change_ticks`/`body_change_wall_ms` 从工具/伤害触发到实测身体变化。GameTestServer 加速推进游戏刻，墙钟毫秒仅为测试进程诊断，不能当作玩家实际等待；按正常 20 TPS 折算也只是理论游戏时长。停止的变化指“连续三刻确认停稳”，不是取消包发出的时刻。没有给这些不同场景合算 P95。
- 尚无用户体验 SLA，当前超时是防止运行失控的边界，不是“玩家可接受等待”的标准。第一条正确回复、真实模型、UI 到身体延迟保持 `null`，不能用 0 填缺失值。

评分逻辑及期望总量不作为模型输入。本地模型调用预算为 0；没有使用作者模型、额外供应商或模型评分器。真实 Minecraft 外部认证服务的后台尝试不属于模型调用。

## 记录与复现

每次产出：

- `manifest.json`：该次冻结的样例、标准、用途和预算。
- `run.json`：源码候选、Git HEAD 和脏工作树状态、环境摘要、实际命令、退出码、时长。
- `source-hashes.json`、`candidate.patch`：含未跟踪新源码的摘要及当时已跟踪文件的修改；评测源码随本目录及测试类一起交付。基线包含用户本来已有的未提交修改，并非纯 HEAD。
- `raw/*.jsonl`：原始逐例证据，含动作轨迹或身体初末状态。
- `results.jsonl`：固定全部 28 个 ID；未跑、失败、设施异常都保留。
- `summary.json`：分层得分、完整性、记录错误、已观测调用消耗。
- `agent.log`、`gametest.log`：执行日志；JUnit XML 同时保留在 Gradle 的报告目录。

`evaluation_version` + `evaluation_sha256` 固定样例/评分/运行代码；`environment_sha256` 单独标识依赖和运行环境；候选由 HEAD + 实际源码摘要标识。比较时这些评测和环境标识必须相同。每行由这些标识加 `candidate/split/case_id/rep` 确定，不能跨环境混合汇总。

缺行、重复、未知 ID、错误版本、缺少证据、源码在运行中变化都会判运行无效。正常得到错误行为是 `ok + success=false`；身体崩溃/超时等为 `system_failure`；准备失败或没有执行结果为 `infra_error`。实际模型调用/费用为 0，机器和助手消耗无法完整观测，`total_cost=null`。

后续若修改评分、配方或世界夹具，需要新评测版本并重测基线。此轮没有 hillclimb、候选择优或生产策略修复。

## 后续优先补齐

1. 将真实客户端的玩家输入、第一条正确回复、工具派发、服务端受理和身体变化串成一次 trace，沿用用户绑定的模型和认证；先约定调用数预算。
2. 四类完整能力场景：从零准备材料/工具/工作站，多目标共享库存，冶炼期间做其他工作并回收产物，资源失效后的高层重规划。
3. 低血量逃跑、挖矿途中返回/停止，以及“取出产物”这类不能只靠成功回执评分的终局验证。
4. 建议再加业务约束：权限被拒后的替代方案、背包满/工具损坏时诚实汇报、断线/死亡后不重复执行、不得虚报完成。先少量各一例，避免用大量同类简单题掩盖缺口。

历史 bundled skill 与当时工具用法的差异仍保留在原始运行记录中；此次入口适配没有修改产品提示词或使用真实模型。
